4. GAME ARCHITECTURE / RULES
========================
Server is authoritative for shared multiplayer actions:
- WebSocket players, teams, position updates, nearby vision snapshots.
- Combat damage, ability validation, cooldowns, energy, statuses, death/respawn.
- Resource-node availability, harvesting validation, respawn timers.
- Player economy inventory, crafting recipes, factories/production, trader transactions.
- Factories and world resource updates are broadcast to relevant players.
The browser renders the world and sends requests; do not trust client-provided damage, item quantities, ownership, recipe outputs, movement claims, or team privileges. Keep server and client item/recipe identifiers aligned.

The HTTP server serves the main HTML at / and the health probe at /healthz. The multiplayer WebSocket is at /multiplayer. When adding browser assets, explicitly add HTTP routes; files in the repository are not automatically served.

The map includes a river. Server-side movement/resource rules include river blocking and bridge crossings. Keep client visuals and server collision rules aligned.

6. LOBBY DESIGN AND PROTOCOL
========================
The supplied lobby prototype is a simple pre-match lobby:
- Connection view asks for display name and server address; defaults to current host.
- Room view lists Blue/Red teams, player readiness, team changes, host and Start button.
- First connected player is host; host can start once all other players are ready.
- Lobby is not a room browser: no multiple rooms, invite codes, password-protected rooms, chat, account persistence, or reconnect identity yet.
- Team cap is derived from max players / 2; current max is 40 (20 per team).
- Client API: Lobby.mount({ defaultServer, send, onConnect, onLeave, onStart }) and Lobby.handle(message).
- WebSocket URL is /multiplayer; lobby client normalizes host or ws/wss URL.
- Lobby protocol:
  client -> server:
    lobby-get
    lobby-team { team: "blue" | "red" | "auto" }
    lobby-ready { ready: boolean }
    lobby-start (host only)
    lobby-reset (host only)
  server -> client:
    lobby-state { phase, hostId, you, maxPerTeam, canStart, players:[{id,name,team,ready,host}] }
    lobby-started
    lobby-error { message }
- Server should reject gameplay actions while phase is lobby; allow only connection/setup/lobby messages and any intentionally allowed harmless setup requests. Client should not send position state, movement, or attack commands while the lobby overlay is visible.
- Team changes must update both the lobby list and the in-game team/friendly-fire visuals/target filtering. Be careful: the generic broadcast function vision-filters player payloads and expects x/z; a partial player object without coordinates may not reach clients. Use lobby-state as authoritative team information or broadcast a complete public-player snapshot.
- If host disconnects, choose a new host and publish state.
- A late join during a running match needs a deliberate UX: either allow it into game and hide lobby, or reject it. Keep server and client behavior consistent.
- On match start, hide lobby and trigger any deferred initial economy request. Avoid duplicate state changes if lobby-started and lobby-state(phase=playing) both invoke start callbacks.
- Avoid calling localStorage when embedding this client in non-browser tests; it runs in the browser, so this is currently okay.

ARENA3D — NEAR-TERM TASK BACKLOG (priority order)

P0 — Stabilize navigation and portal traversal
1. Reproduce and fully diagnose bots getting stuck at portals after v71. Determine whether they stop before the entrance, fail to appear/leave at the exit, oscillate between regions, or get blocked by portalLock. Trace portalPoint, navBuildRoute, navWaypoint, go, routeBotTo, squadTravelTo, portal transition code and all relevant callers.
2. Add robust stuck detection based on lack of positional progress, not merely elapsed task time. On failure: invalidate cached portal/waypoint, rebuild route, try another reachable portal approach/exit, and apply bounded retries. Avoid infinite route-rebuild loops.
3. Ensure portalLock prevents immediate bounce-back but expires or clears when the bot has safely moved away. Check that the exit point itself is reachable and that the next waypoint is in the correct region.
4. Add lightweight debug visibility/logging for bot ID, current region, target region, current task, portal side, route length, waypoint index, stuck duration and retry count. Make it possible to disable verbose logs.
5. Test several bots with different spawn positions and obstacles, plus travel in both directions and concurrent portal use. Do not mark fixed based on syntax validation alone.

P1 — Make logistics physical and economically consistent
1. Replace instant resource withdrawal with a real bot task: the bot travels to the main faction warehouse, reaches a valid interaction point, loads the required materials into its bag, then travels to the destination/workshop.
2. Deduct stock only at successful physical loading. Support partial loads, bag capacity, missing resources, unavailable routes, interrupted trips and retry behavior without duplicating or losing items.
3. Keep global faction stock, regional localStock, caravan cargo and bot bag inventories distinct. Define and document which source each task is allowed to use; do not silently treat a regional depot as the main warehouse.
4. Bots are substitutes for human players and their resurrection/respawn consumes resources too. Model bot resurrection costs explicitly and calculate whether expected faction income can sustain player and bot respawns plus crafting, upgrades and other spending. Avoid infinite free bot replacement or an economy that permanently starves the faction.
5. Show useful feedback where possible: stock at warehouse, stock in transit, stock delivered, and unavailable materials.

P2 — Improve strategic army AI
1. Allow multiple independent squads when army size and available manpower justify it. Each squad needs its own target, task state, route, retry timer and member list; prevent the same bot from being assigned to multiple squads.
2. Support simultaneous operations: attack multiple suitable regions, defend threatened territory and escort logistics units without every squad overwriting one faction-wide target.
3. Prefer neutral adjacent regions when expansion is safe and useful; attack enemy territory when neutral options are unavailable or strategic conditions justify it.
4. After a successful capture, assign a garrison sized according to threat and keep the remaining force available for the next operation.
5. When a friendly region is attacked, recall or redirect nearby available forces and garrisons according to urgency. Do not abandon every front for a minor threat.
6. If a squad cannot form, find a route or reach its target, release invalid assignments and reform/reassign it. Try alternate paths and portals before giving up.
7. Keep the 12-second capture-hold behavior (if still present in current source) explicit and configurable. Define how interrupted capture progress behaves and prevent one-frame/brief presence from capturing a region.

P3 — Economy and world simulation depth
1. Add clear resource production chains and make regional specialization meaningful.
2. Make workshops and construction consume delivered materials and worker time rather than silently consuming distant stock.
3. Add regional trade routes and caravan scheduling only after physical warehouse/depot logistics is reliable.
4. Add population/workers, food upkeep and region development only with a sustainable resource budget and clear UI feedback.
5. Consider commanders, unit roles, scouting, morale and siege equipment after core navigation, logistics and multi-squad AI are stable.

- Captured regions receive a deliberate garrison assignment; threatened regions can request help without corrupting other squads' tasks.
